# BUG-010：切换代理出口后 ChatGPT 出现访问验证与 Work 云端异常

记录日期：2026-11-03。状态：大阪自建节点下用户报告功能恢复；新机场下普通 ChatGPT 可用，**Work 云端是否完全恢复尚未确认**。官方修复状态及根因均未确认。

## 1. 我的场景与问题

我在 Windows 上使用 ChatGPT 桌面端、Chrome 网页版和 Clash Verge。原机场节点此前可以正常使用 ChatGPT；搭建 Evoxt 大阪自建节点并使用一段时间后，我切回原机场，遇到以下现象：

- 桌面端出现“无法锁定模式”；普通聊天偶尔显示“未知错误”或“无法加载此聊天”。
- Work 云端无法加载已有对话，也无法创建新对话；Work 本地电脑模式仍可用。
- 我发现原机场多个节点都有类似问题，而不只是单一节点。
- 我切回大阪自建节点后报告上述问题恢复。此前另一次故障也曾在等待约一小时后恢复，因此不能把每次恢复都归因于切换节点。

我希望桌面端能清楚区分会话初始化、访问验证和执行器连接问题。尤其是选择 Work 云端时，界面出现“无法连接到你的桌面执行器。请检查其连接状态后重试”，容易让人误以为本地执行器一定损坏。

## 3. 排查过程与证据

### 出口对照和账号

在同一台电脑和同一 ChatGPT 账号下，我观察到大阪自建节点可用，原机场节点出现异常。新机场下 ChatGPT 也可以正常使用。这支持出口或相关网络路径与故障存在关联；没有发现账号被永久绑定到某个 IP 的证据，但这不是对所有账号状态的完整证明。

对照期间涉及不同出口；早期一次受控测试也表明实际流量路径需要分别核对。不能仅凭这些观察排除连接复用、DNS、路由、验证状态或时间因素。机场所有节点出现类似问题是我的现场观察，并非每个节点均有独立请求日志。

### Cloudflare 验证及实际客户端请求

机场节点下，Chrome 开发者工具的 Network 曾出现 `challenges.cloudflare.com/cdn-cgi/challenge-platform/` 请求，其中一次记录为：

```text
HTTP 401 Unauthorized
Server: cloudflare
WWW-Authenticate: PrivateToken
Cf-Ray: a548aca8a9dd2513-SJC
```

这里的 `PrivateToken` 401 可能是验证过程的一部分，不能单独作为 IP 被封禁的证据。

另一次桌面端实测中，2026-10-29 18:00 附近的会话创建相关请求（包括 `/f/conversation/prepare`、`/sentinel/chat-requirements/prepare` 和 `/conversation/init`）出现 HTTP 403、`cloudflare_challenge`。该轮执行器连接曾显示就绪并保持连接，但仍出现 `Unknown error`；没有捕获足够证据证明用户界面的每个错误都由同一个请求直接触发。请求只保留路径和状态，不公开身份信息、请求体或原始日志。

### 普通聊天请求

## 4. 原因分析与处理结果

**已观察到：**原机场环境出现访问异常；桌面端一次真实会话请求收到验证型 403；我切回大阪节点后报告恢复，新机场下报告 ChatGPT 可用。普通聊天 API 后来可以成功，但新机场下 Work 云端是否完全恢复尚未确认。

**最可能的解释，尚未证实：**原机场出口 IP 或其共享上游网络环境可能更容易触发 Cloudflare 安全验证，并影响部分 ChatGPT 请求。IPPure 的两次分数差异提供辅助线索，不能证明验证规则、实际触发因素或具体请求之间的因果关系。没有证据证明 OpenAI 永久封禁了原机场 IP。

**其他边界：**现有对照不支持直接认定账号永久锁定 IP、Clash Verge 损坏、Hysteria2 配置错误或大阪 VPS 自身故障；也不能完全排除客户端更新、验证状态或网络路径在某些时间点的影响。2026-10-29 客户端更新与故障时间接近，但因果关系未确认。

我的实际处理是使用大阪自建节点，随后更换新机场；没有通过重装软件或修改 DNS 来处理。新机场下普通 ChatGPT 的恢复属于我的使用观察，Work 云端需要另行在新建及已有云端对话中验证发送和回复，不能宣称彻底修复或官方已修复。

## 5. 经验与后续验证

1. IP 风险检测不等于平台实际访问信誉；Google、Cloudflare 和 OpenAI 的安全机制不同。
2. Cloudflare Challenge 不等于永久封禁；`PrivateToken` 401 也不一定表示业务请求失败。
3. 普通聊天请求成功不代表 Work 云端正常，需分别验证加载已有对话及创建新对话并收到回复。
4. 比较不同出口时应记录真实请求、状态码、时间、实际路由和验证结果；切换后留意旧连接可能仍使用原出口。
5. 出现异常时优先做有记录的出口对照，不把重装、修改 DNS 或重新部署 VPS 当成未经验证的首选方案。
