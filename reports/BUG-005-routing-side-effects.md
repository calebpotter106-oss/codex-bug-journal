- QQ 处理记录日期：2026-10-07；国内网站规则调整记录日期：2026-10-10。最早出现慢传输或网站失败的具体时刻未记录。
- 状态：QQ 直连规则验收通过，**实际文件传输速度未验收，慢传输不能标为已解决**；国内网站入口请求验收通过，完整业务流程未验收。
- 官方修复状态：未确认。
- 分类：BUG-003 的网络绕行方案及后续规则调整带来的关联影响，**不是已确认的 Codex 本体缺陷**。两类现象合并记录，不按网站重复计数。

## 2. 我的使用经历与实际影响

我为了让 Codex 能登录、保持连接，需要开着虚拟网卡。但启用后，我使用 QQ 传文件变得很慢。我改成规则模式时，又发现有些网站打不开，不想为了不同应用来回切换。

后来我进一步遇到国内网站也进不去，并指出普通 Chrome 中打开的学习通受影响。我的实际两难是：关闭虚拟网卡影响 ChatGPT/Codex，开启后又影响日常传文件和学习网站。我希望同一套设置能兼顾这些用途。

## 4. 现场条件与复现范围

我在开启 TUN 的情况下使用 QQ 传文件，报告速度很慢；在规则模式与 TUN 开启时访问国内网站，报告无法进入学习通。

没有记录传输文件大小、速率曲线、失败网址全文或统一错误码，也没有独立的干净环境复现。后续有进程路由及网站入口探测，不能替代文件传输和登录后业务验收。

## 5. 最小证据

我的直接描述包括“使用 QQ 传递文件变得非常慢”和“国内网页打不开”。没有应用原始错误码可附。

规则调整后留存的最小证据：

```text
QQ.exe   → ProcessName → DIRECT
QQEX.exe → ProcessName → DIRECT
学习通登录入口 → HTTP 302，DIRECT
学习通课程入口 → HTTP 200，DIRECT
百度入口       → HTTP 200，DIRECT
Codex 账号接口 → HTTP 200
```

## 6. 尝试、结果与操作问题的区分

| 尝试 | 实际结果 | 说明 |
|---|---|---|
| 用全局模式／TUN 维持 Codex | Codex 有可用路径，我报告 QQ 文件慢 | 未测出代理单独造成多少速度损失 |
| 给 QQ 添加直连例外 | 新连接命中 DIRECT，Codex 账号访问仍成功 | 直连策略生效；不是文件速度验收 |
| 初步采用“QQ 以外全部代理” | 后来仍报告国内站点问题 | 这条兜底范围较宽，是本轮配置的局限，不包装成新的 Codex 缺陷 |
| 增加学习通、私网、国内域名与 IP 直连规则，同时保留 OpenAI 代理 | 学习通登录／课程入口及百度请求成功 | 支持入口网络路径可用；未验证视频、作业提交等完整功能 |
| 探测 `www.qq.com` | TLS 阶段失败 | 这是一次网页探测，不能据此认定 QQ 文件服务失败或 QQ 直连无效 |

## 7. 已确认与待验证

- **已确认：**处理后的新 QQ 连接走 DIRECT；指定国内站点入口走 DIRECT，并收到有效响应。
- **配置层面的已确认局限：**初步规则将大量非 QQ 流量统一交给代理，后来针对国内流量收窄了范围。
- **推测：**QQ 慢与绕代理有关，国内站点问题与不合适的路由有关；未做完整性能或应用业务对照，不能写成所有现象的唯一根因。
- **待验证：**修复后 QQ 实际传输速度、学习通登录后的功能、未覆盖网站、订阅／配置切换后的规则保留情况。

## 8. 实际修改与验收

先在当时生效的订阅扩展脚本中添加 `QQ.exe`、`QQEX.exe` 和相关域名直连规则，保留 TUN；再增加国内站点及私网分流，保留 OpenAI 目标代理。修改前留有本机备份与撤销工具，未公开这些完整配置。

已验收的是路由匹配和入口响应，没有代发 QQ 文件，也没有代替我执行学习通完整学习流程。旧连接可能仍保留原路径，不能只看旧传输立即评价新规则。

这些策略依赖当时的配置／订阅；后续节点和配置有变化，本次整理不保证当前沿用。

## 9. 我希望改进的地方

对桌面应用，我希望统一代理支持能减少必须使用全机 TUN 的情况，并提供清晰的连接诊断。对本机网络方案，我希望能直观看到哪些应用和网站走代理、哪些直连，避免以解决 Codex 为目的的宽泛规则影响学习和传文件。
